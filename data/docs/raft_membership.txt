Raft Cluster Membership Changes and Log Compaction

Cluster Membership Changes: Raft supports changing the set of servers participating in the cluster without taking the system offline. The naive approach of switching directly from an old configuration to a new configuration is unsafe, because servers switch configurations at different times, potentially allowing two independent majorities to form during the transition. Raft's original solution uses a two-phase approach called joint consensus: the cluster first transitions to a transitional configuration that includes both the old and new configurations. During joint consensus, agreement for elections and entry commitment requires separate majorities from both the old and new configurations. A simpler and now more widely adopted alternative restricts membership changes to adding or removing a single server at a time, which guarantees that the majorities of any old and new configuration overlap.

Log Compaction: In practical systems, the replicated log cannot grow without bound. Raft uses snapshotting for log compaction. Each server independently takes snapshots covering the committed entries in its log. The snapshot stores the current state of the state machine, plus the last included index and last included term, which identify the last entry in the log that the snapshot replaces. Once a server completes a snapshot, it may delete all log entries up through the last included index. If a follower lags so far behind that the leader has already discarded the log entries it needs, the leader sends the follower an InstallSnapshot RPC transferring the full snapshot.

Client Interaction: Clients of Raft send all of their requests to the leader. If a client contacts a follower, the follower rejects the request and supplies information about the most recent leader it has heard from. To achieve linearizable semantics, each client is assigned a unique identifier and attaches sequence numbers to commands; the state machine tracks the latest sequence number processed for each client and rejects duplicates, which prevents a command from being executed twice if a leader crashes after committing but before responding.
